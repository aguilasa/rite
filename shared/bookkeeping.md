# Bookkeeping — two commits per finished item

Status lives only in item frontmatter; tables are views regenerated by the CLI.

1. **Start**: `rite mark <ID> in-progress` (no commit). Why: an interrupted run resumes the same item.
2. **Work commit**: commit the work (see `commit-policy.md`). Prose you wrote in the item file (Notes,
   results, measured numbers) goes in this commit — but never the frontmatter state fields.
3. **Close**: `rite close <ID> --json`. It reads the work commit (HEAD, or `--sha`), writes `status`,
   `done_on` (the commit's date), `done_commit`, the file list from git into the Execution Log, sets
   `reviewed_on: pending` on tasks, regenerates the views and commits `chore(rite): close <ID>`.
   Why a second commit: a commit cannot contain its own SHA.
4. **Other transitions**: `rite mark <ID> blocked|skipped --reason "..." --commit`;
   `rite mark-reviewed <ID> [--fixes ...]`; `rite mark-stale <FIX> --reason "..."`.
5. **Verify**: `rite check --quick --cycle <cycle>` must be clean before you report. A red check is
   reported, never hidden.

Never: edit `status`, `done_on`, `done_commit`, `reviewed_on` by hand; edit between
`<!-- rite:begin ... -->` and `<!-- rite:end -->`; allocate an ID yourself (`rite new-task` /
`rite new-fix` create the file atomically).
